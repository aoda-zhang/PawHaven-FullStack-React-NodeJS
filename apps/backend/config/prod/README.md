# Production deployment configuration

This directory contains the production Docker and Kubernetes configuration for the four
backend services. The existing NestJS runtime configuration remains under each service's
`src/config/prod/` directory and is not modified.

## Build and push Docker images

Run every build from the repository root so pnpm workspace packages are available:

```bash
docker build -f apps/backend/gateway/config/prod/docker/Dockerfile -t ghcr.io/aoda-zhang/pawhaven-gateway:prod .
docker build -f apps/backend/core-service/config/prod/docker/Dockerfile -t ghcr.io/aoda-zhang/pawhaven-core-service:prod .
docker build -f apps/backend/auth-service/config/prod/docker/Dockerfile -t ghcr.io/aoda-zhang/pawhaven-auth-service:prod .
docker build -f apps/backend/document-service/config/prod/docker/Dockerfile -t ghcr.io/aoda-zhang/pawhaven-document-service:prod .
```

Push all four images to GHCR before applying the Deployments. For repeatable releases,
replace the mutable `:prod` image tags with the exact tags or digests produced by CI.

## Prepare Kubernetes

Create the namespace first:

```bash
kubectl apply -f apps/backend/gateway/config/prod/kubernetes/namespace.yaml
```

Create the `pawhaven-prod-secrets` Secret in that namespace. Keep the populated env file
outside the repository and do not commit it:

```bash
kubectl create secret generic pawhaven-prod-secrets \
  --namespace pawhaven-prod \
  --from-env-file=./prod-secrets.env
```

The env file must define the following keys:

- `JWT_SECRET`
- `INTERNAL_JWT_PRIVATE_KEY`
- `INTERNAL_JWT_PUBLIC_KEY`
- `CORE_SERVICE_MONGODB`
- `AUTH_SERVICE_MONGODB`
- `DOCUMENT_SERVICE_MONGODB`
- `BLOB_PUBLIC_BASE_URL`
- `DOCUMENT_READ_WRITE_TOKEN`
- `DOCUMENT_STORE_ID`
- `EMAIL_SMTP_HOST`
- `EMAIL_SMTP_USER`
- `EMAIL_SMTP_PASSWORD`

The internal JWT private/public values must be the matching shared key pair generated by
`node scripts/generate-internal-jwt-keys.mjs`. The private key is used by gateway and
core-service; the public key is used by auth-service, core-service, and document-service.

Apply each service independently:

```bash
kubectl apply -k apps/backend/gateway/config/prod/kubernetes
kubectl apply -k apps/backend/core-service/config/prod/kubernetes
kubectl apply -k apps/backend/auth-service/config/prod/kubernetes
kubectl apply -k apps/backend/document-service/config/prod/kubernetes
```

All four Services are `ClusterIP`; internal services are not exposed directly. No Ingress
is created. Connect the existing Traefik / Cloudflare Tunnel routing to the gateway separately.

## Operational notes

- Each Deployment sets `NODE_ENV=production`, which the application's runtime environment
  resolver maps to the existing `prod` configuration under `src/config/prod`.
- Internal host variables use full in-cluster origins with ports. PawHaven's current HTTP
  client only appends a configured port for localhost hosts.
- The repository does not currently implement `/health`, `/health/live`, or
  `/health/ready`. The manifests use TCP socket probes: these verify that a process is
  listening, not that MongoDB or downstream services are healthy.
- document-service renders PDFs with Puppeteer/Chromium. Its image installs the Debian
  browser runtime libraries and persists Puppeteer's downloaded browser under the non-root
  runtime user's home directory.
- document-service has a larger memory limit and temporary volume than the other services.
- Resource values are initial single-node settings, not a validated capacity plan. A
  2 vCPU / 2 GiB ECS instance is tight for K3s plus all four services, especially during
  PDF rendering. Check actual memory usage and OOM events before treating this sizing as
  production-ready.
