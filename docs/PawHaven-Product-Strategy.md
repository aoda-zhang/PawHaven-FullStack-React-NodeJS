## 1. 产品定位与用户画像

### 1.1 核心问题

> 一只流浪动物从被发现到被领养，中间经历 "发现→上报→救助→治疗→康复→领养" 六个环节。目前这些环节高度碎片化——发现者不知道该联系谁、救助者无法及时获取信息、领养者找不到可靠渠道。**信息断裂导致救助效率低下，很多本可以获救的动物错过了最佳救助窗口。**

### 1.2 产品使命

**让每一条流浪生命都被看见、被救助、被善待。**

PawHaven 不做"又一个宠物社区"。它是一张协作网络——把发现者、救助者（个人志愿者/救助站）、医疗机构、领养者串联在一个透明的流程上。

### 1.3 四类核心用户

| 用户角色 | 一句话描述 | 核心诉求 | 使用频率 |
|----------|-----------|----------|----------|
| **发现者 (Reporter)** | 路人/居民，发现流浪动物想帮忙但不知道怎么做 | "我该找谁？怎么上报？这动物受伤了怎么办？" | 低频（偶发事件） |
| **救助者 (Rescuer)** | 个人志愿者或救助站工作人员，实际执行救助 | "附近有新案例吗？谁在处理？需要我介入吗？" | 高频（日常工作） |
| **领养者 (Adopter)** | 想领养流浪动物的人，希望找到靠谱的渠道 | "这动物健康吗？性格怎么样？领养流程是什么？" | 中频（决策周期长） |
| **知识贡献者 (Contributor)** | 兽医、资深救助人，分享专业知识 | "我写的救助指南有人看吗？我的经验能帮到人吗？" | 低频（内容生产） |

> **关键洞察**: 一个用户可能同时扮演多个角色。今天你是发现者，明天你可能是领养者，后天你可能是救助者。产品需要支持这种**角色流动性**。

### 1.4 与竞品的差异化

| 维度 | 传统宠物领养平台 | 社交媒体求助 | **PawHaven** |
|------|----------------|------------|-------------|
| 信息结构化 | 仅展示可领养动物 | 碎片化帖子 | **全流程结构化（上报→救助→领养）** |
| 救助透明度 | 无 | 无 | **7阶段状态追踪，每一步公开** |
| 协作机制 | 无 | 评论区自发 | **志愿者认领 + 救助站对接** |
| 知识沉淀 | 无 | 散落帖子 | **结构化救助知识库** |
| 信任基础 | 依赖平台背书 | 依赖个人信誉 | **公开救助记录 = 天然信任链** |

## 3. 模块一 · 流浪动物上报

### 3.1 模块定位

**"3 分钟内完成一次有效的流浪动物上报"** —— 让没有任何救助经验的普通人也能提供有效信息。

### 3.2 核心业务流程

```
发现流浪动物
    │
    ▼
┌──────────────┐     ┌─────────────┐     ┌──────────────┐
│ ① 拍摄/上传   │ ──→ │ ② 位置标记   │ ──→ │ ③ 基础信息    │
│   照片       │     │ GPS/手动输入 │     │ 动物类型/数量 │
└──────────────┘     └─────────────┘     └──────────────┘
                                                 │
                                                 ▼
┌──────────────┐     ┌─────────────┐     ┌──────────────┐
│ ⑥ 提交成功   │ ←── │ ⑤ 紧急程度   │ ←── │ ④ 状态评估    │
│ 告知后续流程 │     │ 需立即救援？  │     │ 受伤/被困/健康│
└──────────────┘     └─────────────┘     └──────────────┘
        │
        ▼
  系统自动通知附近志愿者 / 救助站
        │
        ▼
  案例进入"救助进程追踪"模块
```

### 3.3 关键设计决策

**为什么是 6 步而非单页表单？**
- 发现者通常处于紧张/着急的状态。分步引导降低认知负载。
- 每一步只问一件事：先拍照（最自然）、再定位（GPS 自动获取）、再描述。
- 每步都可以跳过非必填项，但关键信息（照片 + 位置 + 类型）必填。

**"紧急程度"的判断逻辑**
- 系统不会让发现者自己判断"是否需要救援"（容易误判）。
- 改为结构化问题：动物是否在流血？是否无法移动？是否在危险位置（马路中间/高速路）？
- 任何一个"是" → 自动标记为 **紧急** → 优先推送通知。

**上报成功后的即时反馈**
- 不是冷冰冰的"提交成功"。而是告诉用户：
  1. "我们已经通知了附近的 XX 名志愿者和 X 个救助站"
  2. "你可以追踪这个案例的后续进展（点击查看）"
  3. "如果想了解更多救助知识，可以看这篇指南"
- 目标：让发现者感到"我做了有用的事"，而不是"我填了个表"。

### 3.4 上报案例的数据模型（核心字段）

| 字段组 | 字段 | 必填 | 说明 |
|--------|------|------|------|
| 媒体 | 照片 (1-5张) | ✅ | 第一张作为封面 |
| 位置 | GPS 坐标 + 文字地址 | ✅ | GPS 自动获取，地址可编辑 |
| 基础 | 动物类型 (猫/狗/其他) | ✅ | 其他时可填写具体类型 |
| 基础 | 数量 | - | 一窝幼崽的情况 |
| 状态 | 外观特征 (毛色/体型) | - | 帮助识别 |
| 状态 | 紧急指标 (流血/无法移动/危险位置) | ✅ | 自动判定紧急程度 |
| 状态 | 行为特征 (亲近人/警惕/有攻击性) | - | 帮助救助者做准备 |
| 联系 | 发现者联系方式 | - | 可选，用于后续跟进 |
| 联系 | 是否愿意参与后续救助 | - | 转化为潜在志愿者 |

## 4. 模块二 · 救助进程追踪

### 4.1 模块定位

**"让每一次救助都有始有终"** —— 从上报到结局的全程透明追踪，是平台信任的基础。

### 4.2 救助状态机（7 阶段）

```
   ┌─────────┐
   │ Pending │ ← 发现者上报，等待响应
   │  待响应  │
   └────┬────┘
        │ 志愿者/救助站认领
        ▼
   ┌─────────┐
   │InProgress│ ← 救助者已出发 / 正在救助
   │  救助中  │
   └────┬────┘
        │ 动物已安全转移
        ▼
   ┌─────────┐
   │ Treated │ ← 已接受初步医疗（清洁/包扎/检查）
   │  已治疗  │
   └────┬────┘
        │ 进入康复期
        ▼
   ┌─────────┐
   │Recovering│ ← 在救助站/寄养家庭恢复中
   │  康复中  │
   └────┬────┘
        │
   ┌────┴────────────┐
   │                 │
   ▼                 ▼
┌──────────┐   ┌──────────┐
│ Awaiting │   │  Failed  │ ← 未能存活 / 走失 / 无法救助
│ Adoption │   │  已结束   │
│ 待领养   │   └──────────┘
└────┬─────┘
     │ 领养成功
     ▼
┌──────────┐
│ Adopted  │
│ 已领养   │
└──────────┘
```

### 4.3 每个状态下的核心交互

| 状态 | 谁在行动 | 核心交互 |
|------|---------|----------|
| **Pending** | 系统 + 志愿者 | 系统推送通知给附近志愿者；志愿者浏览案例并"认领"；发现者可补充信息 |
| **In Progress** | 救助者 | 救助者更新进展（文字+照片）；记录救助方式（诱捕/网捕/直接抱走） |
| **Treated** | 救助者 + 医疗机构 | 上传医疗记录（疫苗/驱虫/手术）；记录治疗费用（可选公开，支持捐赠） |
| **Recovering** | 救助站/寄养家庭 | 定期更新康复照片；记录行为评估（性格/习惯/适合领养的条件） |
| **Awaiting Adoption** | 系统 + 领养者 | 发布领养信息；领养者浏览和申请；救助站审核 |
| **Adopted** | 领养者 + 系统 | 领养者上传"新家第一天"照片；案例标记为完成；邀请撰写爱心故事 |
| **Failed** | 救助者 | 记录原因（尊重事实，不责备）；可选择公开或不公开详情；对救助者的情感支持提示 |

### 4.4 为什么状态机是这个模块的核心

- **透明度建立信任**: 每一个状态变更都有时间戳和操作人记录。领养者可以看一只动物从被发现到可领养的全过程——这是最好的信任凭证。
- **协作的信号机制**: 状态告诉所有参与者"现在需要谁"。Pending → 需要志愿者。Recovering → 需要耐心。Awaiting Adoption → 需要领养者。
- **防止"僵尸案例"**: 如果一个案例在某个状态停留超过预期时间（如 Pending 超过 24 小时），系统自动提升优先级或通知更多志愿者。

### 4.5 救助时间线 (Timeline)

每个救助案例都有一个公开的**时间线视图**，按时间倒序展示所有状态变更：

```
2025-06-15 14:30  🏠 已领养  — 张先生领养了小白，新家在朝阳区
2025-06-10 09:00  ⏳ 待领养  — 小白已完成疫苗接种，开放领养
2025-06-03 16:00  💚 康复中  — 伤口愈合良好，开始正常进食
2025-06-01 11:00  💉 已治疗  — 爱心宠物医院完成伤口处理和疫苗
2025-06-01 08:30  🔵 救助中  — 志愿者李明到达现场，已将猫安全转移
2025-06-01 07:15  ⚠️ 待响应  — 陈女士在花园路发现一只受伤白猫
```

## 5. 模块三 · 爱心故事

### 5.1 模块定位

**"让每一次成功的救助都成为更多人行动的理由"** —— 爱心故事是平台的"情感引擎"，驱动更多人参与。

### 5.2 核心业务流程

```
救助案例标记为"已领养"
        │
        ▼
系统自动邀请 ──→ 救助者 / 领养者撰写故事
        │
        ▼
┌────────────────────────────────────┐
│ 故事编辑器（结构化 + 自由撰写）       │
│                                    │
│ ① 标题："从垃圾桶到沙发 —— 小橘的180天"│
│ ② Before/After 对比照             │
│ ③ 故事正文（支持富文本 + 图片穿插）   │
│ ④ 关键数据自动带入（救助时长/参与人数）│
│ ⑤ 标签（#车祸幸存 #橘猫 #三脚猫勇士） │
└────────────────────────────────────┘
        │
        ▼
  发布审核（防滥用）
        │
        ▼
┌────────────────────────────────────┐
│ 故事展示                            │
│ · 首页"精选故事"轮播                │
│ · 故事列表页（按标签/动物类型筛选）   │
│ · 关联原始救助案例（可追溯全过程）    │
│ · 互动：点赞/评论/分享              │
└────────────────────────────────────┘
```

### 5.3 为什么需要这个模块（而非简单列表）

**情感驱动行为**。数据告诉我们：
- 理性信息（"XX 只动物等待领养"）驱动 20% 的行动
- 情感故事（"这只猫在垃圾桶里被发现，现在它有了家"）驱动 80% 的行动

**故事 → 行动转化链**：
```
阅读故事 → 被打动 → 浏览可领养动物 → 提交领养申请
         → 被打动 → 了解救助知识 → 发现流浪动物 → 上报
         → 被打动 → 想帮忙 → 注册成为志愿者
```

### 5.4 故事的内容策略

| 故事类型 | 示例 | 目标情感 | 目标行动 |
|----------|------|---------|----------|
| **Before/After** | 从受伤流浪到新家的蜕变 | 希望、感动 | 领养浏览 |
| **救助纪实** | 一场深夜救援的完整记录 | 敬佩、共鸣 | 成为志愿者 |
| **领养日记** | 领养后的 30 天记录 | 温暖、信任 | 领养申请 |
| **知识科普** | "我第一次救助流浪猫踩的 5 个坑" | 学习、共情 | 阅读知识库 |
| **社区故事** | 一个小区居民集体救助流浪猫群 | 社区感、参与感 | 上报/分享 |

## 6. 模块四 · 救助知识库

### 6.2 知识分类体系

```
救助知识库
├── 🚨 紧急情况
│   ├── 发现受伤动物怎么办
│   ├── 车祸动物的急救处理
│   ├── 中毒动物的识别与处理
│   └── 如何安全接近有攻击性的动物
│
├── 🐱 猫科救助
│   ├── 幼猫救助完全指南
│   ├── 成年流浪猫 TNR（捕捉-绝育-放归）指南
│   ├── 猫常见疾病的识别
│   └── 如何判断猫是否适合领养
│
├── 🐕 犬科救助
│   ├── 流浪狗救助安全指南
│   ├── 犬瘟/细小的识别与隔离
│   └── 大型犬的运输与安置
│
├── 📋 救助流程
│   ├── 第一次救助的完整 checklist
│   ├── 如何联系救助站和动保组织
│   ├── 救助物资清单（常备什么）
│   └── 救助相关的法律法规
│
├── 🏠 领养与安置
│   ├── 领养审核标准参考
│   ├── 新宠到家：前 7 天指南
│   └── 多宠家庭的引入技巧
│
└── 💡 经验分享
    ├── 资深救助者的故事与心得
    ├── 各地救助资源汇总（用户贡献）
    └── 常见误区与避坑指南
```

### 6.3 核心业务流程

```
┌────────────────┐
│ 知识贡献者撰写  │ ← 认证兽医 / 资深救助者 / 平台编辑
│ (结构化编辑器)  │
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ 审核流程        │ ← 内容审核（准确性 + 安全性）
│ (专家审核)      │   医疗建议必须标注"仅供参考，请咨询兽医"
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ 知识发布        │
│ · 分类索引      │
│ · 搜索（全文）  │
│ · 关联救助案例  │ ← "关于 TNR，你可以参考这个案例..."
│ · 相关文章推荐  │
│ · 可下载 PDF    │ ← 离线阅读，方便在户外参考
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ 知识反馈        │
│ · "这篇有用吗？" │ ← 收集反馈，优化内容
│ · 评论与讨论    │
│ · 贡献补充信息  │ ← 用户可以在评论区补充经验
└────────────────┘
```

### 6.4 关键设计决策

**为什么需要审核？**
救助知识涉及动物生命安全。错误的建议（如"用人类药给猫吃"）可能致命。每条知识必须：
- 经过至少一位认证兽医/资深救助者审核
- 医疗建议附带免责声明
- 标注"经验性知识"还是"兽医专业知识"

**知识库与救助流程的联动**
- 当用户上报流浪动物时，根据上报的"动物类型"和"紧急指标"，自动推荐相关知识
- 例：上报"受伤的猫" → 推荐"发现受伤动物怎么办"+"幼猫/成猫救助指南"
- 当志愿者认领案例时，推荐"救助 checklist"和"联系附近救助站"的知识

## 7. 模块五 · 领养匹配

### 7.1 模块定位

**"不是展示列表，而是做匹配"** —— 基于领养者的生活条件和偏好，匹配合适的动物，提高领养成功率、降低退养率。

### 7.2 核心业务流程

```
┌──────────────────────────────────────┐
│          领养者端                     │
│                                      │
│  浏览可领养动物 ← 关联救助案例全过程    │
│       │                              │
│       ▼                              │
│  查看动物详情                          │
│  · 救助全过程时间线（透明度 = 信任）     │
│  · 康复记录 + 医疗记录                │
│  · 行为评估（性格/习惯/特殊需求）       │
│  · 救助者/救助站信息                  │
│       │                              │
│       ▼                              │
│  提交领养申请                          │
│  · 基本信息（居住情况/养宠经验/家庭成员） │
│  · 领养意向（为什么想领养这只？）       │
│  · 上传居住环境照片（可选）            │
│       │                              │
└───────┼──────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────┐
│          救助站端                     │
│                                      │
│  收到申请 → 审核 → 沟通 → 面试/家访    │
│       │                              │
│       ▼                              │
│  决定：通过 / 拒绝（附原因） / 待定     │
│       │                              │
│       ▼                              │
│  通过 → 签署领养协议 → 交接动物        │
│       → 救助案例标记为"已领养"         │
│       → 邀请撰写爱心故事              │
└──────────────────────────────────────┘
```

### 7.3 匹配算法（轻量版）

不是复杂的推荐算法，而是**条件过滤 + 权重排序**：

| 匹配维度 | 权重 | 说明 |
|----------|------|------|
| 领养者偏好（类型/年龄/体型） | ⭐⭐⭐⭐⭐ | 硬匹配 |
| 地理位置距离 | ⭐⭐⭐⭐ | 就近原则，方便回访 |
| 领养者经验匹配度 | ⭐⭐⭐ | 新手 → 推荐性格温顺的；经验者 → 可推荐需要特殊照顾的 |
| 动物等待时间 | ⭐⭐ | 等待越久，适当提高权重（但不是主要因素） |
| 居住条件匹配 | ⭐⭐⭐⭐ | 公寓不适合大型犬；有小孩的家庭需要性格稳定的动物 |

### 7.4 退养预防机制

> 领养后退养对动物是二次伤害。预防退养比处理退养更重要。

| 环节 | 预防措施 |
|------|---------|
| **申请时** | 必填领养动机和居住条件；教育性提示（"领养是 15 年的承诺"） |
| **审核时** | 救助站与领养者充分沟通；告知动物的特殊需求和潜在问题 |
| **交接时** | 提供"新宠到家指南"（关联知识库）；签署协议 |
| **领养后** | 7 天/30 天/90 天回访提醒；领养者可在平台记录"新家日记" |

## 8. 模块六 · 志愿者协作

### 8.1 模块定位

**"让想帮忙的人知道该怎么帮"** —— 志愿者不是"注册就完事"，而是有一个清晰的能力画像和任务匹配系统。

### 8.2 志愿者能力模型

```
志愿者画像
├── 基础信息
│   ├── 所在城市/区域（核心！决定推送范围）
│   ├── 可出动时间（工作日晚上/周末全天/随时）
│   └── 交通方式（步行/自行车/汽车 → 决定响应半径）
│
├── 救助能力
│   ├── 经验等级（新手/有经验/资深/专业兽医）
│   ├── 擅长类型（猫/狗/小型动物）
│   ├── 可执行任务（现场救助/运输/临时寄养/协助捕捉）
│   └── 认证状态（是否通过平台身份认证）
│
├── 救助统计
│   ├── 参与救助次数
│   ├── 成功救助次数
│   ├── 响应速度（平均认领时间）
│   └── 评价（来自发现者/救助站）
│
└── 偏好设置
    ├── 是否接收紧急通知
    ├── 通知半径（5km/10km/全城）
    └── 是否愿意临时寄养
```

### 8.3 核心业务流程

```
发现者上报案例（标记位置）
        │
        ▼
系统匹配 ──→ 筛选半径内 + 能力匹配 + 在线状态的志愿者
        │
        ▼
推送通知 ──→ "距离你 2.3km 有一只受伤的猫需要救助"
        │
        ▼
志愿者查看案例 → 决定"认领"或"不参与"
        │
        ▼
认领后 ──→ 案例状态变为 In Progress
        │  → 其他志愿者看到"已有 1 人处理中"
        │  → 可申请"协助"（如需要多人配合）
        │
        ▼
救助完成 ──→ 更新案例状态
          → 志愿者获得救助积分/成就
          → 救助记录计入个人统计
```

### 8.4 志愿者激励体系

不是游戏化（gamification），而是**意义感驱动 + 轻度成就感**：

| 激励方式 | 具体实现 |
|----------|---------|
| **救助记录** | 个人主页展示"你帮助过 X 只动物" |
| **感谢系统** | 发现者和领养者可以给志愿者发送感谢信 |
| **能力成长** | 从"新手"到"资深"，反映实际经验 |
| **社区认可** | 月度优秀志愿者展示（需志愿者同意） |
| **优先信息** | 高活跃志愿者可以提前看到新案例 |

## 9. 模块七 · 个人中心与成就

### 9.1 模块定位

**"你的每一次善举都被记录"** —— 个人中心是用户在这个平台上的"身份"和"足迹"。

### 9.2 用户身份聚合

由于一个用户可能同时是发现者、志愿者、领养者，个人中心需要聚合所有这些身份的数据：

```
个人中心
├── 📊 我的数据
│   ├── 我上报的案例（X 个，其中 Y 个已成功救助）
│   ├── 我参与的救助（X 次志愿者行动）
│   ├── 我领养的动物
│   └── 我撰写的爱心故事（X 篇，共获得 Y 次点赞）
│
├── 🏅 我的成就（轻量徽章）
│   ├── "第一次上报" / "第一次救助" / "第一次领养"
│   ├── "救助达人"（参与 10+ 次救助）
│   ├── "故事大王"（撰写 5+ 篇爱心故事）
│   ├── "知识贡献者"（贡献了 X 篇知识库文章）
│   └── "社区英雄"（被感谢 X 次）
│
├── 📝 我的动态
│   ├── 我关注的救助案例进展
│   ├── 我上报的案例有新进展
│   └── 我收藏的知识/故事
│
└── ⚙️ 设置
    ├── 通知偏好
    ├── 志愿者状态（在线/暂离/长期不可用）
    └── 隐私设置（哪些信息公开）
```

### 9.3 为什么需要成就系统

不是为了"游戏化"。而是因为：
1. **身份锚定**: "我是一个参与了 15 次救助的志愿者" → 这是真实身份，不是虚拟等级
2. **新手引导**: 成就引导用户发现平台的功能（"你还没上报过流浪动物哦"）
3. **信任凭证**: 领养者看到救助者有"救助达人"成就 → 更信任

### 10.3 MVP 阶段的最小可行功能集

> 核心原则：**先让一条救助能走通，再扩展其他模块。**

| 功能 | 优先级 | 理由 |
|------|--------|------|
| 流浪动物上报（含照片+GPS+紧急指标） | P0 | 信息的入口，没有上报就没有一切 |
| 救助案例浏览（列表+详情+时间线） | P0 | 让志愿者能看到需要救助的动物 |
| 7 阶段状态流转 | P0 | 救助的"脊椎"，没有状态就无法协作 |
| 基础用户注册/登录 | P0 | 身份识别 |
| 个人中心（我的上报/我的救助） | P1 | MVP 可以不完善，但需要基本展示 |
| 志愿者认领案例 | P1 | 核心协作动作 |
| 案例状态更新（文字+照片） | P1 | 救助者更新进展 |
| 附近案例推送通知 | P2 | 可以先手动浏览，后期加推送 |
| 爱心故事 | P3 | 需要有成功的救助案例后才能产出故事 |
| 领养匹配 | P3 | 需要有"待领养"状态的动物积累 |
| 知识库 | P2 | 可以先有 5-10 篇核心文章 |

## 附录：关键设计原则

1. **移动优先**: 发现者通常用手机上报，志愿者在户外用手机查看案例。所有核心流程必须移动端友好。

2. **离线友好**: 救助场景可能网络不稳定。上报表单应支持离线草稿，GPS 信息缓存。

3. **安全第一**: 不公开发现者的精确 GPS（只显示大概区域）；不公开志愿者的手机号（站内信沟通）；动物位置信息在救助完成后自动模糊化。

4. **信息真实性**: 上报必须有照片；志愿者身份可选认证（但不强制，降低参与门槛）；领养者需要提交真实信息。

5. **情感安全**: "Failed"状态的展示尊重动物和救助者；不允许在评论区攻击救助者（"你为什么不早点去"）；提供救助者情感支持资源。
